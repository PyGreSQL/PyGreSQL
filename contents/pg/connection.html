Connection – The connection object¶

class pg.Connection¶

This object handles a connection to a PostgreSQL database. It embeds and hides all the parameters that define this connection, thus just leaving really significant parameters in function calls.

Note

Some methods give direct access to the connection socket. Do not use them unless you really know what you are doing. Some other methods give access to large objects. Refer to the PostgreSQL user manual for more information about these.

A connection must not be used concurrently by different threads. While a command is running on the connection, trying to run another command on it or to close or reset it raises a pg.InterfaceError, e.g. when this is done by another thread or by a notice receiver. The only method that may be called by another thread while a command is running is Connection.cancel(). Code that is called back while a command is running in the same thread, i.e. a notice receiver or the iterable passed to Connection.inserttable(), may also use the methods that only return local information, such as Connection.transaction(), Connection.parameter() and the escape methods.

Changed in version 6.3: Using a connection while one of its commands is running raises an error instead of hanging or crashing.

query – execute a SQL command string¶

Connection.query(command[, args])¶

Execute a SQL command string

Parameters:

  • command (str or bytes) – SQL command

  • args – optional parameter values

Returns:

result values

Return type:

Query, str or None

Raises:

  • TypeError – bad argument type, or too many arguments

  • TypeError – invalid connection

  • ValueError – empty SQL query

  • pg.DatabaseError – error in query (a subclass depending on the SQLSTATE, e.g. pg.ProgrammingError)

  • pg.OperationalError – the connection has been lost

This method simply sends a SQL query to the database. If the query is an insert, update or delete statement, the number of rows affected is returned as a string. If it is a statement that returns rows as a result (usually a select statement, but maybe also an "insert/update ... returning" statement), this method returns a Query. Otherwise, it returns None.

You can use the Query object as an iterator that yields all results as tuples, or call Query.getresult() to get the result as a list of tuples. Alternatively, you can call Query.dictresult() or Query.dictiter() if you want to get the rows as dictionaries, or Query.namedresult() or Query.namediter() if you want to get the rows as named tuples. You can also simply print the Query object to show the query results on the console.

The SQL command may optionally contain positional parameters of the form $1, $2, etc instead of literal data, in which case the values must be supplied separately as a tuple. The values are substituted by the database in such a way that they don’t need to be escaped, making this an effective way to pass arbitrary or unknown data without worrying about SQL injection or syntax errors. None is passed as NULL. Strings are encoded with the client encoding, bytes are passed unchanged as the text representation of the value in the client encoding. Values wrapped with Hstore() are converted to hstore literals, in which keys and values given as bytes are also passed unchanged. All other objects are converted to strings with str() and then also encoded with the client encoding, except for objects of the types bytearray and memoryview, which raise a TypeError since their string representation is not their content. Binary data must be wrapped with Bytea(). It is then sent unchanged in binary format as a parameter of type bytea and may contain any bytes, including NUL bytes, which are not allowed in the other parameters. Other values like lists and dictionaries are not adapted to PostgreSQL types, see Parameters of query() and query_prepared() for how to pass such values.

Changed in version 6.3: Values wrapped with Bytea() are sent as binary data. Before, they were passed as text like plain bytes. Objects of the types bytearray and memoryview raise a TypeError. Before, their string representation was sent.

If you don’t pass any parameters, the command string can also include multiple SQL commands (separated by semicolons). You will only get the return value for the last command in this case.

When the database could not process the query, a subclass of pg.DatabaseError corresponding to the SQLSTATE error code is raised, e.g. a pg.ProgrammingError for a syntax error, a pg.DataError for a division by zero or a pg.IntegrityError for a unique constraint violation. You can check the SQLSTATE error code of this error by reading its sqlstate attribute.

Example:

name = input("Name? ")
phone = con.query("select phone from employees where name=$1",
    (name,)).getresult()

send_query – executes a SQL command string asynchronously¶

Connection.send_query(command[, args])¶

Submits a command to the server without waiting for the result(s).

Parameters:

  • command (str or bytes) – SQL command

  • args – optional parameter values

Returns:

a query object, as described below

Return type:

Query

Raises:

  • TypeError – bad argument type, or too many arguments

  • TypeError – invalid connection

  • pg.OperationalError – the connection has been lost

This method is much the same as Connection.query(), except that it returns without waiting for the query to complete. The application can do other things in the meantime, including executing queries using other database connections. The application can call select() using the fileno obtained by the connection’s Connection.fileno() method to determine when the query has results to return.

This method always returns a Query object. This object differs from the Query object returned by Connection.query() in a few ways. Most importantly, the results of all statements are returned, one after the other, and errors in the query (such as an empty query) are only raised when the result of the failing statement is fetched.

The methods that return the whole result, i.e. Query.getresult(), Query.dictresult(), Query.namedresult(), Query.scalarresult() and the corresponding iterator methods, move to the next result and return it. They return None when all results have been returned, and the application should call them until they return None or raise an exception. Otherwise, the connection stays busy until another command is executed (see below). The iterators returned by these methods only iterate over the result that was current when they were created.

In cases when Connection.query() would return something other than a Query object, that result will be returned by these methods. There’s one important difference in these result codes: if Connection.query() returns None, these methods will return an empty string ('') instead, since None marks the end of the results.

All other methods and operations, i.e. getting single rows with Query.one(), Query.single() and their variants, iterating over the query, getting rows by index, len() and the methods that return information about the fields, access the current result without moving to the next result, like they do for queries returned by Connection.query(). When no result has been fetched yet, they fetch the first result, which will then also be returned by the next call of one of the methods returning the whole result. When the current result is not a query result, there are no fields and no rows.

When another command is executed on the connection, e.g. with Connection.query() or Connection.send_query(), before all results have been fetched, the remaining results are fetched and kept in the query object, so that they can still be returned afterwards. Note that this waits for the asynchronous query to complete. If the connection is closed or reset before all results have been fetched, these results are lost and trying to fetch them raises an error.

If a statement is a COPY command, an empty string is returned as its result. Before the next result can be fetched, the data must be sent using Connection.putline() and Connection.endcopy(), or received using Connection.getline() until it returns None. The COPY must also be completed before another command can be executed on the connection, otherwise a pg.InterfaceError is raised.

A query object and its connection must not be used concurrently by different threads. If a query object is used again while its results are being fetched or converted, e.g. by another thread or by a cast hook or notice receiver, a pg.InterfaceError is raised.

Changed in version 6.3: The row accessors, len() and iteration do not move to the next result any more, and results are not discarded any more when another command is executed on the connection.

Added in version 5.2.

Examples:

name = input("Name? ")
query = con.send_query("select phone from employees where name=$1",
                       (name,))
phone = query.getresult()
query.getresult()  # to close the query

# Run two queries in one round trip:
# (Note that you cannot use a union here
# when the result sets have different row types.)
query = con.send_query("select a,b,c from x where d=e;"
                       " select e,f from y where g")
result_x = query.dictresult()
result_y = query.dictresult()
query.dictresult()  # to close the query

# Using select() to wait for the query to be ready:
query = con.send_query("select pg_sleep(20)")
r, w, e = select([con.fileno(), other, sockets], [], [])
if con.fileno() in r:
    results = query.getresult()
    query.getresult()  # to close the query

# Concurrent queries on separate connections:
con1 = connect()
con2 = connect()
s = con1.query("begin; set transaction isolation level repeatable read;"
               "select pg_export_snapshot();").single()
con2.query("begin; set transaction isolation level repeatable read;"
           f"set transaction snapshot '{s}'")
q1 = con1.send_query("select a,b,c from x where d=e")
q2 = con2.send_query("select e,f from y where g")
r1 = q1.getresult()
q1.getresult()
r2 = q2.getresult()
q2.getresult()
con1.query("commit")
con2.query("commit")

query_prepared – execute a prepared statement¶

Connection.query_prepared(name[, args])¶

Execute a prepared statement

Parameters:

  • name (str or bytes) – name of the prepared statement

  • args – optional parameter values

Returns:

result values

Return type:

Query, str or None

Raises:

  • TypeError – bad argument type, or too many arguments

  • TypeError – invalid connection

  • ValueError – empty SQL query

  • pg.DatabaseError – error in query (a subclass depending on the SQLSTATE, e.g. pg.ProgrammingError)

  • pg.OperationalError – prepared statement does not exist, or the connection has been lost

This method works exactly like Connection.query() except that instead of passing the command itself, you pass the name of a prepared statement. An empty name corresponds to the unnamed statement. You must have previously created the corresponding named or unnamed statement with Connection.prepare(), or an pg.OperationalError will be raised.

The types of the parameters have been determined when the statement was prepared. Values wrapped with Bytea() are sent as binary data, so they can only be passed for parameters of type bytea. Use a cast like $1::bytea in the prepared statement if the type cannot be derived from the context.

Added in version 5.1.

prepare – create a prepared statement¶

Connection.prepare(name, command[, types])¶

Create a prepared statement

Parameters:

  • name (str or bytes) – name of the prepared statement

  • command (str or bytes) – SQL command

  • types (list or tuple of int or None) – optional OIDs of the parameter types

Return type:

None

Raises:

  • TypeError – bad argument types, or wrong number of arguments

  • TypeError – invalid connection

  • ValueError – name or command contains NUL characters

  • ValueError – invalid type OID

  • pg.ProgrammingError – error in query or duplicate query

This method creates a prepared statement with the specified name for the given command for later execution with the Connection.query_prepared() method. The name can be empty to create an unnamed statement, in which case any pre-existing unnamed statement is automatically replaced; otherwise a pg.ProgrammingError is raised if the statement name is already defined in the current database session.

The SQL command may optionally contain positional parameters of the form $1, $2, etc instead of literal data. The corresponding values must then later be passed to the Connection.query_prepared() method separately as a tuple.

The server infers the types of the parameters from the context. If this is not possible or not what you want, you can pass the types of the parameters as a list or tuple of type OIDs with the types argument, which can also be passed as a keyword argument. Types given as None or 0, and types of parameters beyond the length of the list, are still inferred by the server. If you pass more types than the command has parameters, the statement expects that many values when it is executed. For instance, the following statement adds two integers:

con.prepare('add', "select $1 + $2", [23, 23])

The OID of a type can be found in the pg_type system catalog, e.g. with a query like select 'int'::regtype::oid. DB.prepare() also accepts type names.

Added in version 5.1.

Changed in version 6.3: The optional types argument has been added.

reset – reset the connection¶

Connection.reset()¶

Reset the pg connection

Return type:

None

Raises:

  • TypeError – too many (any) arguments

  • TypeError – invalid connection

  • pg.InterfaceError – the connection is busy

  • pg.ConnectError – the connection could not be established again (a subclass of pg.OperationalError)

This method resets the current database connection, i.e. it closes the connection to the server and opens a new one with the same parameters. The state of the session on the server, such as open transactions, prepared statements, temporary tables and open large objects, is lost, and session settings such as the date style have their default values again. Results of an asynchronous query that have not yet been fetched are discarded, but the results of other queries remain available.

Changed in version 6.3: A pg.ConnectError is raised if the connection could not be established again. Before, the failure passed silently.

poll – completes an asynchronous connection¶

Connection.poll()¶

Complete an asynchronous pg connection and get its state

Returns:

state of the connection

Return type:

int

Raises:

  • TypeError – too many (any) arguments

  • TypeError – invalid connection

  • pg.ConnectError – the connection could not be established (a subclass of pg.OperationalError)

The database connection can be performed without any blocking calls. This allows the application mainline to perform other operations or perhaps connect to multiple databases concurrently. Once the connection is established, it’s no different from a connection made using blocking calls.

The required steps are to pass the parameter nowait=True to the pg.connect() call, then call Connection.poll() until it either returns POLLING_OK or raises an exception. Before each call of Connection.poll(), use select() or poll() to wait for the connection to be readable or writable, depending on the return code of the previous call to Connection.poll(). This is required by libpq: calling Connection.poll() too early can stall the connection attempt. The initial state of the connection is POLLING_WRITING. The possible states are defined as constants in the pg module (POLLING_OK, POLLING_FAILED, POLLING_READING and POLLING_WRITING).

Added in version 5.2.

Example:

con = pg.connect('testdb', nowait=True)
fileno = con.fileno()
rd = []
wt = [fileno]
rc = pg.POLLING_WRITING
while rc not in (pg.POLLING_OK, pg.POLLING_FAILED):
    ra, wa, xa = select(rd, wt, [], timeout)
    if not ra and not wa:
        timedout()
    rc = con.poll()
    if rc == pg.POLLING_READING:
        rd = [fileno]
        wt = []
    else:
        rd = []
        wt = [fileno]

cancel – abandon processing of current SQL command¶

Connection.cancel()¶

Abandon processing of the current SQL command

Returns:

1 (the request has been sent)

Return type:

int

Raises:

  • TypeError – too many (any) arguments

  • TypeError – invalid connection

  • pg.OperationalError – the request could not be sent

  • pg.InterfaceError – the connection is being established

This method requests that the server abandon processing of the current SQL command. It can be called by another thread while the command is running. If the request has been sent, the command fails with an error if it was still running, but the server may also have finished processing it already. If the request could not be sent, a pg.OperationalError with the reason given by libpq is raised. The method always returns 1 otherwise, for backward compatibility.

The request is sent over a new connection to the server, and other threads can run while it is sent. If PyGreSQL has been built with libpq 17 or newer, the request uses the same encryption settings as the connection, and connecting is limited by the connect_timeout of the connection. Otherwise, the request is sent unencrypted, and without a timeout.

Changed in version 6.3: The request is sent without blocking other threads and, with libpq 17 or newer, encrypted like the connection. If the request could not be sent, an error is raised instead of returning 0. Before, the method used the deprecated PQrequestCancel() function of libpq, which is not thread-safe.

close – close the database connection¶

Connection.close()¶

Close the pg connection

Return type:

None

Raises:

  • TypeError – too many (any) arguments

  • pg.InternalError – the connection has already been closed

  • pg.InterfaceError – the connection is busy

This method closes the database connection. The connection will be closed in any case when the connection is deleted but this allows you to explicitly close it. After the connection has been closed, its other methods and its attributes cannot be used any more and raise a TypeError, and large objects of the connection cannot be used either. Results of an asynchronous query that have not yet been fetched are discarded, but the results of other queries remain available.

transaction – get the current transaction state¶

Connection.transaction()¶

Get the current in-transaction status of the server

Returns:

the current in-transaction status

Return type:

int

Raises:

  • TypeError – too many (any) arguments

  • TypeError – invalid connection

The status returned by this method can be TRANS_IDLE (currently idle), TRANS_ACTIVE (a command is in progress), TRANS_INTRANS (idle, in a valid transaction block), or TRANS_INERROR (idle, in a failed transaction block). TRANS_UNKNOWN is reported if the connection is bad. The status TRANS_ACTIVE is reported only when a query has been sent to the server and not yet completed.

parameter – get a current server parameter setting¶

Connection.parameter(name)¶

Look up a current parameter setting of the server

Parameters:

name (str or bytes) – the name of the parameter to look up

Returns:

the current setting of the specified parameter

Return type:

str or None

Raises:

  • TypeError – bad argument type, or wrong number of arguments

  • TypeError – invalid connection

Certain parameter values are reported by the server automatically at connection startup or whenever their values change. This method can be used to interrogate these settings. It returns the current value of a parameter if known, or None if the parameter is not known.

You can use this method to check the settings of important parameters such as server_version, server_encoding, client_encoding, application_name, is_superuser, session_authorization, DateStyle, IntervalStyle, TimeZone, integer_datetimes, and standard_conforming_strings.

Values that are not reported by this method can be requested using DB.get_parameter().

Added in version 4.0.

date_format – get the currently used date format¶

Connection.date_format()¶

Look up the date format currently being used by the database

Returns:

the current date format

Return type:

str

Raises:

  • TypeError – too many (any) arguments

  • TypeError – invalid connection

This method returns the current date format used by the server. Note that it is cheap to call this method, since there is no database query involved and the setting is also cached internally. You will need the date format when you want to manually typecast dates and timestamps coming from the database instead of using the built-in typecast functions. The date format returned by this method can be directly used with date formatting functions such as datetime.strptime. It is derived from the current setting of the database parameter DateStyle.

Added in version 5.0.

escape_literal/identifier/string/bytea – escape for SQL¶

The connection also has the methods escape_literal(), escape_identifier(), escape_string() and escape_bytea(), which escape strings for direct use in SQL commands, taking the properties of the connection such as the client encoding into account. They work exactly like the methods of the same name of the DB wrapper, see DB.escape_literal(), DB.escape_identifier(), DB.escape_string() and DB.escape_bytea().

encrypt_password – encrypt a password¶

Connection.encrypt_password(password, user, algorithm=None)¶

Encrypt a password for the given user

Parameters:

  • password (str or bytes) – the password in clear text

  • user (str or bytes) – the name of the user

  • algorithm (str, bytes or None) – the encryption algorithm, or None for the server setting

Returns:

the encrypted password

Return type:

str

Raises:

  • TypeError – bad argument type, or too many arguments

  • TypeError – invalid connection

  • ValueError – an argument contains NUL characters

  • ValueError – unknown algorithm

  • UnicodeEncodeError – the user name cannot be encoded

  • pg.InterfaceError – the connection is busy

  • pg.OperationalError – the connection has been lost

  • pg.ProgrammingError – the server setting cannot be read

This method returns the password in the encrypted form that is stored in the server, e.g. SCRAM-SHA-256$4096:... or md5.... It can be used in the PASSWORD clause of the SQL commands CREATE ROLE and ALTER ROLE, so that the password itself is not sent to the server, where it could appear in the server log or in pg_stat_activity. Use the method escape_literal() (see DB.escape_literal()) to insert it into the SQL command.

The algorithm can be 'scram-sha-256' or 'md5'. Note that MD5 encrypted passwords are deprecated since PostgreSQL 18. If algorithm is None, the server setting password_encryption is used, which is queried from the server. The encryption itself is done on the client by libpq (PQencryptPasswordConn()). The user name is only used by the MD5 algorithm, but must always be passed.

A password given as a string is always encoded as UTF-8, regardless of the client encoding, since passwords are also sent as UTF-8 when connecting with pg.connect() and SCRAM expects UTF-8 passwords. A user name given as a string is encoded with the client encoding. Both can also be passed as bytes, which are used unchanged. Note that the MD5 algorithm uses the user name as salt, while the server uses the name in the server encoding, so with MD5, non-ASCII user names only work if the client encoding is the same as the server encoding (libpq has the same limitation).

Example:

encrypted = con.encrypt_password(password, 'bob')
con.query(f"CREATE ROLE bob LOGIN PASSWORD"
          f" {con.escape_literal(encrypted)}")

Added in version 6.3.

change_password – change the password of a user¶

Connection.change_password(user, password)¶

Change the password of the given user

Parameters:

  • user (str or bytes) – the name of the user

  • password (str or bytes) – the new password in clear text

Return type:

None

Raises:

  • TypeError – bad argument type, or too many arguments

  • TypeError – invalid connection

  • ValueError – an argument contains NUL characters

  • UnicodeEncodeError – the user name cannot be encoded

  • pg.InterfaceError – the connection is busy

  • pg.OperationalError – the connection has been lost

  • pg.ProgrammingError – the password could not be changed

This method encrypts the password like Connection.encrypt_password() with the algorithm from the server setting password_encryption and sends it with an ALTER USER command to the server, so that the password itself is never sent to the server. With libpq 17 or newer, this is done by the libpq function PQchangePassword().

The password and the user name are encoded like in Connection.encrypt_password(). The command runs in the current transaction, if one is open, so that the change only takes effect after it is committed. Users can always change their own password. Changing the password of another user needs the CREATEROLE privilege (and since PostgreSQL 16 the ADMIN option on that role), or superuser privileges if the other user is a superuser. The method raises a pg.ProgrammingError if the command fails, e.g. because the user does not exist, which you can check with the sqlstate attribute of the error.

Added in version 6.3.

getnotify – get the last notify from the server¶

Connection.getnotify()¶

Get the last notify from the server

Returns:

last notify from server

Return type:

tuple, None

Raises:

  • TypeError – too many parameters

  • TypeError – invalid connection

This method tries to get a notify from the server (from the SQL statement NOTIFY). If the server returns no notify, the method returns None. Otherwise, it returns a tuple (triplet) (relname, pid, extra), where relname is the name of the notification channel, pid is the process id of the connection that triggered the notify, and extra is a payload string that has been sent with the notification. Remember to do a listen query first, otherwise Connection.getnotify() will always return None.

The name and the payload are decoded with the client encoding. Like text values, a payload that cannot be decoded (e.g. non-ASCII text with the client encoding SQL_ASCII) is returned as bytes.

Changed in version 4.1: Support for payload strings was added in version 4.1.

Changed in version 6.3: The name and the payload are decoded with the client encoding.

inserttable – insert an iterable into a table¶

Connection.inserttable(table, values, [columns, ]*, freeze=False)¶

Insert a Python iterable into a database table

Parameters:

  • table (str or bytes) – the table name

  • values (list) – iterable of row values, which must be lists or tuples

  • columns (list) – list or tuple of column names (None = all columns)

  • freeze (bool) – if True, immediately freeze the inserted rows

Return type:

int

Raises:

  • TypeError – invalid connection, bad argument type, or too many arguments

  • MemoryError – insert buffer could not be allocated

  • ValueError – unsupported values, values or names containing NUL characters, or an error reported by the server

  • UnicodeEncodeError – a string that cannot be encoded in the client encoding

  • OSError – the data could not be sent to the server

This method allows you to quickly insert large blocks of data in a table. Internally, it uses the COPY command of the PostgreSQL database. The method takes an iterable of row values which must be tuples or lists of the same size, containing the values for each inserted row. These may contain strings, bytes, None for NULL values, and any other objects whose string representation is a valid input for the column type, such as integers, floats, booleans, decimal.Decimal, uuid.UUID, date, time, datetime and timedelta objects, objects of the ipaddress module, and values wrapped with Json() or Hstore(). Strings are encoded with the client encoding, bytes are passed unchanged as the text representation of the value in the client encoding. Other objects are converted like query parameters (see Connection.query()), i.e. to hstore literals or with str(), and then also encoded with the client encoding. Objects of the types bytearray and memoryview raise a TypeError. The values must not contain NUL characters, which PostgreSQL does not support in text. Binary data for columns of type bytea must be wrapped with Bytea(); it is then sent in the hex format of bytea and may contain any bytes, including NUL bytes. table is the table name, optionally qualified with a schema name (see Table names). The table and column names can also be passed as bytes, which are not encoded, e.g. for non-ASCII names with the client encoding SQL_ASCII. columns is an optional tuple or list of column names to be passed on to the COPY command. The number of rows affected is returned.

Warning

This method doesn’t type check the fields according to the table definition; it just looks whether or not it knows how to handle such types.

Connection.set_notice_receiver(func)¶

Set a custom notice receiver

Parameters:

func – the custom notice receiver callback function or None

Return type:

None

Raises:

TypeError – the specified notice receiver is neither callable nor None

This method allows setting a custom notice receiver callback function. When a notice or warning message is received from the server, or generated internally by libpq, and the message level is not below the one set with client_min_messages, the specified notice receiver function will be called. This function must take one parameter, the Notice object, which provides the following read-only attributes:

Notice.pgcnx¶

the connection (None after the receiver has returned)

Notice.message¶

the full message with a trailing newline

Notice.severity¶

the level of the message, e.g. 'NOTICE' or 'WARNING'

Notice.primary¶

the primary human-readable error message

Notice.detail¶

an optional secondary error message

Notice.hint¶

an optional suggestion what to do about the problem

str(notice) returns the full message. The notice object can be kept and used after the receiver has returned, but its Notice.pgcnx attribute is then None. Exceptions raised by the receiver cannot be propagated to the code that caused the notice, so they are passed to sys.unraisablehook() instead, which by default prints them to sys.stderr.

The receiver is called in the middle of a libpq operation on the connection, e.g. while a query is running. Therefore it must not run queries or other commands on the connection, and must not close it; trying this raises a pg.InterfaceError. It may set another notice receiver, though.

If you set the notice receiver to None, the default notice receiver of libpq is restored, which prints the messages to sys.stderr. To ignore all notices, set a receiver that does nothing instead.

Added in version 4.1.

Changed in version 6.3: The notice can be used after the receiver has returned, exceptions raised by the receiver are reported as unraisable, setting the receiver to None restores the default receiver, and using the connection in the receiver raises an error instead of hanging.

getline – get a line from server socket¶

Connection.getline()¶

Get a line from server socket

Returns:

the line read, or None at the end of the copy operation

Return type:

str, bytes or None

Raises:

  • TypeError – invalid connection

  • TypeError – too many parameters

  • OSError – no COPY in progress or other error reading the line

  • pg.DatabaseError – the COPY failed (at the end)

This method allows you to directly read a string from the server socket. The line is decoded with the client encoding. Like text values, a line that cannot be decoded is returned as bytes. A final newline is removed, so this method is only suited for the text and CSV formats of COPY. Use the getdata() method of the source object for the binary format.

At the end of the COPY, the final result of the command is fetched, so that the connection can be used again, and an error is raised if the COPY failed. If the COPY was started with Connection.send_query(), the final result is returned by the query object instead.

Changed in version 6.3: The line is decoded with the client encoding instead of UTF-8. An OSError instead of a MemoryError is raised when no COPY is in progress, and the connection is idle after the COPY.

endcopy – synchronize client and server¶

Connection.endcopy()¶

Synchronize client and server

Return type:

None

Raises:

  • TypeError – invalid connection

  • TypeError – too many parameters

  • OSError – no COPY in progress or other error ending the COPY

  • pg.DatabaseError – the COPY failed

The use of direct access methods may desynchronize client and server. This method ensures that client and server will be synchronized.

After the data has been sent with Connection.putline(), this method ends the COPY and fetches the final result of the command, so that the connection can be used again, and raises an error if the COPY failed, e.g. because of invalid data. If the COPY was started with Connection.send_query(), the final result is returned by the query object instead.

Changed in version 6.3: Errors of the COPY are raised, and the connection is idle afterwards.

Object attributes¶

Every Connection defines a set of read-only attributes that describe the connection and its status. These attributes are:

Connection.host¶

the host name of the server (str)

This is 'localhost' if the connection uses a Unix-domain socket.

Connection.hostaddr¶

the IP address of the server (str)

This is the address the host name has been resolved to, or the address given with the hostaddr connection parameter. It is empty if the connection uses a Unix-domain socket.

Added in version 6.3.

Connection.port¶

the port of the server (int)

Connection.db¶

the selected database (str)

Connection.options¶

the connection options (str)

Connection.user¶

user name on the database system (str)

Connection.protocol_version¶

the major version of the frontend/backend protocol being used (int)

Added in version 4.0.

Connection.full_protocol_version¶

the full version of the frontend/backend protocol being used (int)

The version is given as the major version times 10000 plus the minor version, e.g. 30002 for version 3.2, which can be used with PostgreSQL 18 and newer if it is allowed with the max_protocol_version connection parameter. If PyGreSQL has been built with a libpq older than version 18, the minor version cannot be determined and is returned as 0.

Added in version 6.3.

Connection.server_version¶

the backend version (int, e.g. 150004 for 15.4)

Added in version 4.0.

Connection.encoding¶

the name of the Python codec used for the client encoding (str)

This is the codec that is used to encode text sent to the server and to decode text received from the server, e.g. 'utf-8' for the client encoding UTF8. For SQL_ASCII and for client encodings that are not supported by Python, this is 'ascii'.

Added in version 6.3.

Connection.status¶

the status of the connection (int: 1 = OK, 0 = bad)

Connection.error¶

the last warning/error message from the server (str)

Connection.socket¶

the file descriptor number of the connection socket to the server (int)

Added in version 5.1.

Connection.backend_pid¶

the PID of the backend process handling this connection (int)

Added in version 5.1.

Connection.ssl_in_use¶

this is True if the connection uses SSL, False if not

Added in version 5.1.

Connection.ssl_attributes¶

SSL-related information about the connection (dict)

Added in version 5.1.
