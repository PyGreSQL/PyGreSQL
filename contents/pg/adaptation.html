Remarks on Adaptation and Typecasting¶

Both PostgreSQL and Python have the concept of data types, but there are of course differences between the two type systems. Therefore PyGreSQL needs to adapt Python objects to the representation required by PostgreSQL when passing values as query parameters, and it needs to typecast the representation of PostgreSQL data types returned by database queries to Python objects. Here are some explanations about how this works in detail in case you want to better understand or change the default behavior of PyGreSQL.

Supported data types¶

The following automatic data type conversions are supported by PyGreSQL out of the box. If you need other automatic type conversions or want to change the default conversions, you can achieve this by using the methods explained in the next two sections.

The first element of the array will always be the first element of the Python list, no matter what the lower bound of the PostgreSQL array is. The information about the start index of the array (which is usually 1 in PostgreSQL, but can also be different from 1) is ignored and gets lost in the conversion to the Python list. If you need that information, you can request it separately with the array_lower() function provided by PostgreSQL.

The special values infinity and -infinity of the types date, timestamp, timestamptz and interval (the latter since PostgreSQL 17) are returned as the max and min values of the corresponding Python types, e.g. timedelta.max and timedelta.min for intervals. Note that these values are passed as ordinary finite values when you use them as parameters.

Changed in version 6.3: Infinite intervals are returned as timedelta.max and timedelta.min instead of raising a ValueError.

Values of the unsigned 64-bit type oid8 (since PostgreSQL 19) are returned as int. Pass values above the range of int8 as parameters, but not inline, since PostgreSQL has no cast from numeric to oid8.

Changed in version 6.3: Values of the type oid8 are returned as int instead of str.

Values of the network address types inet and cidr are returned as strings. As parameters, you can also pass objects of the ipaddress module, also as elements of lists and tuples: addresses and interfaces are adapted as inet, networks as cidr.

If you want to get such objects back instead of strings, you can set the typecast functions cast_inet and cast_cidr from the pg.cast module (see the section on typecasting below):

>>> from pg.cast import cast_cidr, cast_inet
>>> pg.set_typecast('inet', cast_inet)
>>> pg.set_typecast('cidr', cast_cidr)

Like in psycopg 3, cast_inet returns an interface for values with a prefix length such as 192.168.0.1/24, and an address for other values.

Changed in version 6.3: Objects of the ipaddress module can be passed as inline parameters, and the typecast functions cast_inet and cast_cidr were added.

Text encoding¶

Strings are encoded and decoded with the client encoding of the connection (the PostgreSQL setting client_encoding) as follows:

  • Queries, parameters, names of prepared statements, table and column names and data for COPY are encoded with the client encoding. A string that cannot be encoded raises a UnicodeEncodeError, e.g. non-ASCII text with the client encoding SQL_ASCII. You can always pass bytes instead, which are sent unchanged. Queries, parameters and names, and strings passed to the escape methods, must not contain NUL characters, they raise a ValueError instead of being truncated. Strings written to large objects are always encoded as UTF-8, since the server stores large objects without conversion.

  • Text values returned by the database are decoded to str. With the client encoding SQL_ASCII, PostgreSQL does not convert text and its actual encoding is unknown, so values that are not plain ASCII are returned as bytes instead. This also applies to the elements of arrays, records and hstore values, to the payload of notifications, and to the lines returned by Connection.getline() or decoded by the getdata() method of the source object (used by Cursor.copy_to() in pgdb). JSON values are then passed to the JSON decoder as bytes, which json.loads() decodes as UTF-8.

  • Such raw text can be written back unchanged. When bytes are passed as parameters for a known type other than bytea, they are regarded as raw text in the client encoding and sent unchanged, see below. This also applies to the elements of arrays, the fields of records and the keys and values of hstore values. The other parts of such values are then encoded with the client encoding, which is available as the Python codec name in the Connection.encoding attribute. Hstore values passed directly as parameters to Connection.query() and the other query methods, or to Connection.inserttable(), are converted in the same way.

  • Field names, error messages, notices, notification channels and parameter values (Connection.parameter()) are always str. If they cannot be decoded with the client encoding, they are decoded as UTF-8 with backslash escapes for invalid bytes (e.g. the byte 0xE4 becomes the four characters \xe4). The names returned by Query.listfields() can always be passed to Query.fieldnum() or Query.fieldinfo().

The PostgreSQL encodings are mapped to the corresponding Python codecs, e.g. WIN1252 to cp1252. Encodings that are not supported by Python are handled like SQL_ASCII: strings must be plain ASCII, and text values that are not plain ASCII are returned as bytes. A UnicodeWarning is issued when the connection is used with such a client encoding (once, and again only after the client encoding has been changed).

Changed in version 6.3: Undecodable text values are returned as bytes again, also as elements of arrays and records. Field names, error messages, notifications and parameter values are decoded with the client encoding. Names of prepared statements and data for COPY are encoded with the client encoding. Strings with NUL characters raise a ValueError. PostgreSQL encodings that have different names in Python can be used.

Adaptation of parameters¶

When you use the higher level methods of the classic pg module like DB.insert() or DB.update(), you don’t need to care about adaptation of parameters, since all of this is happening automatically behind the scenes. You only need to consider this issue when creating SQL commands manually and sending them to the database using the DB.query() method or similar methods.

Imagine you have created a user login form that stores the login name as login and the password as passwd and you now want to get the user data for that user. You may be tempted to execute a query like this:

>>> db = pg.DB(...)
>>> sql = "SELECT * FROM user_table WHERE login = '%s' AND passwd = '%s'"
>>> db.query(sql % (login, passwd)).getresult()[0]

This seems to work at a first glance, but you will notice an error as soon as you try to use a login name containing a single quote. Even worse, this error can be exploited through so-called “SQL injection”, where an attacker inserts malicious SQL statements into the query that you never intended to be executed. For instance, with a login name something like ' OR ''=' the attacker could easily log in and see the user data of another user in the database.

One solution for this problem would be to cleanse your input of “dangerous” characters like the single quote, but this is tedious and it is likely that you overlook something or break the application e.g. for users with names like “D’Arcy”. A better solution is to use the escaping functions provided by PostgreSQL which are available as methods on the DB object:

>>> login = "D'Arcy"
>>> db.escape_string(login)
"D''Arcy"

As you see, DB.escape_string() has doubled the single quote which is the right thing to do in SQL. However, there are better ways of passing parameters to the query, without having to manually escape them. If you pass the parameters as positional arguments to DB.query(), then PyGreSQL will send them to the database separately, without the need for quoting them inside the SQL command, and without the problems inherent with that process. In this case you must put placeholders of the form $1, $2 etc. in the SQL command in place of the parameters that should go there. For instance:

>>> sql = "SELECT * FROM user_table WHERE login = $1 AND passwd = $2"
>>> db.query(sql, login, passwd).getresult()[0]

That’s much better. So please always keep the following warning in mind:

Warning

Remember to never insert parameters directly into your queries using the % operator. Always pass the parameters separately.

If you like the % format specifications of Python better than the placeholders used by PostgreSQL, there is still a way to use them, via the DB.query_formatted() method:

>>> sql = "SELECT * FROM user_table WHERE login = %s AND passwd = %s"
>>> db.query_formatted(sql, (login, passwd)).getresult()[0]

Note that we need to pass the parameters not as positional arguments here, but as a single tuple. Also note again that we did not use the % operator of Python to format the SQL string, we just used the %s format specifications of Python and let PyGreSQL care about the formatting. Even better, you can also pass the parameters as a dictionary if you use the DB.query_formatted() method:

>>> sql = """SELECT * FROM user_table
...     WHERE login = %(login)s AND passwd = %(passwd)s"""
>>> parameters = dict(login=login, passwd=passwd)
>>> db.query_formatted(sql, parameters).getresult()[0]

Here is another example:

>>> sql = "SELECT 'Hello, ' || %s || '!'"
>>> db.query_formatted(sql, (login,)).getresult()[0]

You would think that the following similar example should work, too:

>>> sql = "SELECT %s IS NULL"
>>> db.query_formatted(sql, (login,)).getresult()[0]
ProgrammingError: ERROR:  could not determine data type of parameter $1

The issue here is that DB.query_formatted() by default still uses PostgreSQL parameters, transforming the Python style %s placeholder into a $1 placeholder, and sending the login name separately from the query. In the query we looked at before, the concatenation with other strings made it clear that it should be interpreted as a string. This query however does not give PostgreSQL a clue what data type the $1 placeholder stands for, since any value can be checked for being NULL.

This is different when you are embedding the login name directly into the query instead of passing it as parameter to PostgreSQL. You can achieve this by setting the inline parameter of DB.query_formatted(), like so:

>>> sql = "SELECT %s IS NULL"
>>> db.query_formatted(sql, (login,), inline=True).getresult()[0]

Another way of making this query work while still sending the parameters separately is to simply cast the parameter values:

>>> sql = "SELECT %s::text IS NULL"
>>> db.query_formatted(sql, (login,), inline=False).getresult()[0]

In real world examples you will rarely have to cast your parameters like that, since in an INSERT statement or a WHERE clause comparing the parameter to a table column, the data type will be clear from the context.

Byte strings (bytes) are adapted as binary data of the PostgreSQL type bytea, while str values are adapted as text. If you have text that is already encoded as bytes, decode it to str before passing it. However, when the type of the parameter is known and is not bytea, i.e. when it has been passed with the types parameter or the value is written to a table column with methods like DB.insert(), then bytes are regarded as raw text in the client encoding and sent unchanged. This also applies to the elements of arrays and the fields of records, and always to the keys and values of hstore values. This way, text that PyGreSQL returned as bytes because it could not be decoded can be written back unchanged.

Binary data passed as a parameter of type bytea is sent to the server unchanged in binary format, so it does not need to be escaped and does not depend on settings like standard_conforming_strings. Binary data in arrays and records and binary data passed inline are sent as escaped text, the latter as typed literals like '\x6162'::bytea.

Objects of the types bytearray and memoryview cannot be adapted yet; convert them to bytes before passing them. They raise a TypeError as parameters, as elements of arrays and records and as keys and values of hstore values, and a pg.InterfaceError when they are passed inline. This also applies to the results of __pg_str__ methods (see below), which are called for top-level values and fields of records, but not for elements of arrays. Parameters of type json are an exception: they are passed to the JSON encoder (see DB.encode_json()), which may be able to handle such objects.

Changed in version 6.3: Byte strings were adapted as text in earlier versions, unless they had been wrapped with Bytea(). Binary data was always sent as escaped text. Objects of the types bytearray and memoryview were adapted with str().

A dict could be meant as a value of type json, jsonb or hstore, so its type is not guessed. Wrap it with Json() or Hstore(), or pass its type with the types parameter, otherwise a pg.InterfaceError is raised. This also applies to dictionaries in lists and tuples. Methods like DB.insert() know the types of the columns, so you can pass plain dictionaries there.

Changed in version 6.3: Plain dictionaries without a type were passed as their Python representation in earlier versions, unless they were passed inline.

When adapting the parameters for DB.query_formatted() and the higher level methods, PyGreSQL not only adapts the basic types like int, float, bool and str, but also tries to make sense of Python lists and tuples. Note that DB.query() and DB.query_prepared() do not adapt parameters in this way, see Parameters of query() and query_prepared() below.

Lists are adapted as PostgreSQL arrays:

>>> params = dict(array=[[1, 2],[3, 4]])
>>> db.query_formatted("SELECT %(array)s::int[]", params).getresult()[0][0]
[[1, 2], [3, 4]]

Note that again we need to cast the array parameter or use inline parameters only because this simple query does not provide enough context. Also note that the query gives the value back as Python lists again. This is achieved by the typecasting mechanism explained in the next section.

The elements of the lists are adapted like single values (except that their __pg_str__ methods are not called, see below), so they can also be values wrapped with Json(), UUIDs, IP addresses, or tuples for arrays of composite types.

Tuples are adapted as PostgreSQL composite types. If you use inline parameters, they can also be used with the IN syntax.

Let’s think of a more real world example again where we create a table with a composite type in PostgreSQL:

CREATE TABLE on_hand (
    item      inventory_item,
    count     integer)

We assume the composite type inventory_item has been created like this:

CREATE TYPE inventory_item AS (
    name            text,
    supplier_id     integer,
    price           numeric)

In Python we can use a named tuple as an equivalent to this PostgreSQL type:

>>> from collections import namedtuple
>>> inventory_item = namedtuple(
...     'inventory_item', ['name', 'supplier_id', 'price'])

Using the automatic adaptation of Python tuples, an item can now be inserted into the database and then read back as follows:

>>> db.query_formatted("INSERT INTO on_hand VALUES (%(item)s, %(count)s)",
...     dict(item=inventory_item('fuzzy dice', 42, 1.99), count=1000))
>>> db.query("SELECT * FROM on_hand").getresult()[0][0]
inventory_item(name='fuzzy dice', supplier_id=42, price=Decimal('1.99'))

The DB.insert() method provides a simpler way to achieve the same:

>>> row = dict(item=inventory_item('fuzzy dice', 42, 1.99), count=1000)
>>> db.insert('on_hand', row)
{'item': inventory_item(name='fuzzy dice', supplier_id=42,
        price=Decimal('1.99')), 'count': 1000}

Perhaps we want to use custom Python classes instead of named tuples to hold our values:

>>> class InventoryItem:
...
...     def __init__(self, name, supplier_id, price):
...         self.name = name
...         self.supplier_id = supplier_id
...         self.price = price
...
...     def __str__(self):
...         return '{} (from {}, at ${})'.format(
...             self.name, self.supplier_id, self.price)

But when we try to insert an instance of this class in the same way, we will get an error. This is because PyGreSQL tries to pass the string representation of the object as a parameter to PostgreSQL, but this is just a human readable string and not useful for PostgreSQL to build a composite type. However, it is possible to make such custom classes adapt themselves to PostgreSQL by adding a “magic” method with the name __pg_str__, like so:

>>> class InventoryItem:
...
...     ...
...
...     def __str__(self):
...         return '{} (from {}, at ${})'.format(
...             self.name, self.supplier_id, self.price)
...
...     def __pg_str__(self, typ):
...         return (self.name, self.supplier_id, self.price)

Now you can insert class instances the same way as you insert named tuples. You can even make these objects adapt to different types in different ways:

>>> class InventoryItem:
...
...     ...
...
...     def __pg_str__(self, typ):
...         if typ == 'text':
...             return str(self)
...         return (self.name, self.supplier_id, self.price)
...
>>> db.query("ALTER TABLE on_hand ADD COLUMN remark varchar")
>>> names = db.get_attnames('on_hand', flush=True)  # columns changed
>>> item = InventoryItem('fuzzy dice', 42, 1.99)
>>> row = dict(item=item, remark=item, count=1000)
>>> db.insert('on_hand', row)
{'item': inventory_item(name='fuzzy dice', supplier_id=42,
    price=Decimal('1.99')), 'remark': 'fuzzy dice (from 42, at $1.99)',
    'count': 1000}

Note that we had to flush the cache of the column names of the table after adding the column, otherwise the new column would have been ignored.

There is also another “magic” method __pg_repr__ which does not take the typ parameter. That method is used instead of __pg_str__ when passing parameters inline. You must be more careful when using __pg_repr__, because it must return a properly escaped string that can be put literally inside the SQL. The only exception is when you return a tuple or list, because these will be adapted and properly escaped by PyGreSQL again.

Parameters of query() and query_prepared()¶

The adaptation described above is done by DB.query_formatted() and by the higher level methods like DB.insert(). The lower level methods DB.query() and DB.query_prepared(), like the methods with the same names of the Connection, do not adapt the parameters to their types, which makes them faster. They pass None as NULL, str encoded with the client encoding, bytes unchanged as text, values wrapped with Bytea() as binary data, values wrapped with Hstore() as hstore literals, and all other values as their string representation as returned by str() (see Connection.query() for details).

This is sufficient for all values whose string representation is accepted by PostgreSQL as input for the type of the parameter. This is the case for str, int, float, Decimal and bool values, for objects of the types of the datetime module, for UUID objects and for objects of the ipaddress module. Other values must be adapted before you pass them:

  • Wrap binary data with Bytea(), and values for parameters of the types hstore, json and jsonb with Hstore() and Json(). Otherwise, binary data is passed as text, and dictionaries and lists are passed as their Python representation, which is not valid input for these types.

  • Adapt lists for arrays and tuples for composite types with the method adapt(value, typ) of the DB.adapter. It takes the value and the type of the parameter, given like the types of DB.query_formatted(), and returns the value in the text form that PostgreSQL expects. For a composite type, pass the type object from DB.dbtypes, so that the types of the fields are known. If you pass 'record' instead, the types of the fields are guessed from their values, like for tuples passed without a type. This method can also be used to adapt the values of all other types.

For instance, this is how you pass a list as an array to a prepared statement:

>>> db.prepare('get_items', 'SELECT * FROM on_hand WHERE count = ANY($1)')
>>> counts = db.adapter.adapt([1000, 2000], 'int[]')
>>> counts
'{1000,2000}'
>>> db.query_prepared('get_items', counts).getresult()

And this is how you pass a value of the composite type inventory_item from the example above:

>>> item = inventory_item('fuzzy dice', 42, 1.99)
>>> item = db.adapter.adapt(item, db.dbtypes['inventory_item'])
>>> item
'(fuzzy dice,42,1.99)'
>>> db.query("INSERT INTO on_hand VALUES ($1, $2)", item, 1000)

Note that when you pass a single list or tuple to DB.query() or DB.query_prepared(), it is regarded as the sequence of all parameter values. A list that has not been adapted would therefore be passed as several parameters, which fails with an error like bind message supplies 2 parameters, but prepared statement "get_items" requires 1. This cannot happen with adapted values, since they are strings.

If you don’t need a prepared statement, you can also use DB.query_formatted() instead of DB.query(). It adapts the parameters automatically and, unless you set inline, also sends them to the database separately from the SQL command.

Typecasting to Python¶

As you noticed, PyGreSQL automatically converted the PostgreSQL data to suitable Python objects when returning values via the DB.get(), Query.getresult() and similar methods. This is done by the use of built-in typecast functions.

If you want to use different typecast functions or add your own if no built-in typecast function is available, then this is possible using the set_typecast() function. With the get_typecast() function you can check which function is currently set. If no typecast function is set, then PyGreSQL will return the raw strings from the database.

For instance, you will find that PyGreSQL uses the normal int function to cast PostgreSQL int4 type values to Python:

>>> pg.get_typecast('int4')
<class 'int'>

In the classic PyGreSQL module, the typecasting for these basic types is always done internally by the C extension module for performance reasons. We can set a different typecast function for int4, but it will not become effective, the C module continues to use its internal typecasting.

However, we can add new typecast functions for the database types that are not supported by the C module. For example, we can create a typecast function that casts items of the composite PostgreSQL type used as example in the previous section to instances of the corresponding Python class.

To do this, at first we get the default typecast function that PyGreSQL has created for the current DB connection. This default function casts composite types to named tuples, as we have seen in the section before. We can grab it from the DB.dbtypes object as follows:

>>> cast_tuple = db.dbtypes.get_typecast('inventory_item')

Now we can create a new typecast function that converts the tuple to an instance of our custom class:

>>> cast_item = lambda value: InventoryItem(*cast_tuple(value))

Finally, we set this typecast function, either globally with set_typecast(), or locally for the current connection like this:

>>> db.dbtypes.set_typecast('inventory_item', cast_item)

Now we can get instances of our custom class directly from the database:

>>> item = db.query("SELECT * FROM on_hand").getresult()[0][0]
>>> str(item)
'fuzzy dice (from 42, at $1.99)'

Note that some of the typecast functions used by the C module are configurable with separate module level functions, such as set_decimal(), set_bool() or set_jsondecode(). You need to use these instead of set_typecast() if you want to change the behavior of the C module.

Also note that after changing global typecast functions with set_typecast(), you may need to run db.dbtypes.reset_typecast() to make these changes effective on connections that were already open.

As one last example, let us try to typecast the geometric data type circle of PostgreSQL into a SymPy Circle object. Let’s assume we have created and populated a table with two circles, like so:

CREATE TABLE circle (
    name varchar(8) primary key, circle circle);
INSERT INTO circle VALUES ('C1', '<(2, 3), 3>');
INSERT INTO circle VALUES ('C2', '<(1, -1), 4>');

With PostgreSQL we can easily calculate that these two circles overlap:

>>> q = db.query("""SELECT c1.circle && c2.circle
...     FROM circle c1, circle c2
...     WHERE c1.name = 'C1' AND c2.name = 'C2'""")
>>> q.getresult()[0][0]
True

However, calculating the intersection points between the two circles using the # operator does not work, since PostgreSQL does not support it for circles. So let’s resort to SymPy to find out. To ease importing circles from PostgreSQL to SymPy, we create and register the following typecast function:

>>> from sympy import Point, Circle
>>>
>>> def cast_circle(s):
...     p, r = s[1:-1].rsplit(',', 1)
...     p = p[1:-1].split(',')
...     return Circle(Point(float(p[0]), float(p[1])), float(r))
...
>>> pg.set_typecast('circle', cast_circle)

Now we can import the circles in the table into Python simply using:

>>> circle = db.get_as_dict('circle', scalar=True)

The result is a dictionary mapping circle names to SymPy Circle objects. We can verify that the circles have been imported correctly:

>>> circle['C1']
Circle(Point(2, 3), 3.0)
>>> circle['C2']
Circle(Point(1, -1), 4.0)

Finally we can find the exact intersection points with SymPy:

>>> circle['C1'].intersection(circle['C2'])
[Point(29/17 + 64564173230121*sqrt(17)/100000000000000,
    -80705216537651*sqrt(17)/500000000000000 + 31/17),
 Point(-64564173230121*sqrt(17)/100000000000000 + 29/17,
    80705216537651*sqrt(17)/500000000000000 + 31/17)]
